# Журнал решений

Что решено, почему именно так и где сознательно упрощено. Записи в обратном
хронологическом порядке.

## 2026-09-15 — Внешний адрес для ALLOW_IP определяет приложение

**Решение.** Если в стойке стоит `ALLOW_IP resolve`, FWKOG сам узнаёт внешний
адрес (тот же сервис и то же имя клиента, что у fwknop) и передаёт клиенту уже
конкретный `ALLOW_IP 203.0.113.10`.

**Почему.** В режиме `resolve` клиент fwknop запускает внешнюю программу wget по
пути, зашитому при сборке (`/usr/bin/wget`). На Windows такого пути нет, и стук
падал с «Could not resolve IP via '/usr/bin/wget …'». Вариант «положить рядом
wget» добавил бы в комплект ещё одну чужую программу; вариант «указывать адрес
руками» перекладывает на человека то, что машина знает сама.

**Границы.** Протокол и формат стойки не меняются: «адрес указан явно» — штатный
режим fwknop. Если узнать адрес не вышло, стук не отправляется, а сообщение
предлагает переключиться на «Взять адрес из пакета (source)».

## 2026-09-15 — Вывод клиента читаем кодировкой консоли

**Решение.** Вывод `fwknop` берётся байтами и декодируется кодовой страницей
консоли Windows (`GetOEMCP()`, обычно 866), а не кодировкой системы.

**Почему.** Консольные программы на русской Windows пишут в 866, а Python по
умолчанию разобрал бы их как 1251 — сообщения об ошибках приходили нечитаемой
кашей вместо текста.

## 2026-09-15 — Приложение не реализует SPA, а вызывает клиент fwknop

**Решение.** FWKOG не содержит ни криптографии, ни протокола SPA. Он собирает
стойку и запускает штатный `fwknop`, как это делает человек в командной строке.

**Почему.** Своя реализация протокола — это своя ответственность за ошибки в
криптографии и расхождения с сервером при обновлениях. Начинка должна остаться
ровно той же, что у `fwknop-gui`: цель — удобный интерфейс, а не новый клиент.

## 2026-09-15 — Параметры передаются временным rc-файлом, а не аргументами

**Решение.** Перед стуком стойка пишется во временный файл в каталоге данных
(права 600) и передаётся как `fwknop --rc-file <файл> -n fwkog --no-save-args`.
Файл удаляется сразу после вызова.

**Почему.** Ключи в аргументах командной строки видны в списке процессов любому
процессу того же пользователя. Файл — штатный для fwknop способ, и он же
делает импорт из `~/.fwknoprc` прямым переносом без преобразований.

**Остаточный риск.** Временный файл существует доли секунды и содержит ключи.
Если приложение аварийно завершится ровно в этот момент, файл останется на
диске — поэтому при следующем запуске забытый `.fwkog-run.rc` удаляется.

## 2026-09-15 — Стойка хранится в терминах fwknop, без своей модели

**Решение.** Стойка = имя + словарь переменных `.fwknoprc` (`SPA_SERVER`,
`ACCESS`, `KEY_BASE64`…). Своих полей и своего формата настроек нет.

**Почему.** Любая промежуточная модель — это таблица соответствия, которую
придётся чинить при каждом изменении в fwknop, и потеря переменных, для
которых в интерфейсе не нашлось поля. Сейчас поддержан весь набор: под частые
переменные сделаны поля формы, остальные правятся текстом в блоке «Прочие
переменные».

## 2026-09-15 — Хранилище шифруется мастер-паролем, а не средствами Windows

**Решение.** Стойки лежат в `%LOCALAPPDATA%\FWKOG\configs.enc`: scrypt (пароль
→ ключ) + AES-256-GCM. Пароль спрашивается при запуске.

**Почему.** Штатный `~/.fwknoprc` хранит ключи открытым текстом. Windows
Credential Manager привязывает секреты к машине и учётной записи — перенос
стоек тогда требовал бы ручной работы. Мастер-пароль даёт и защиту на диске,
и переносимость через экспорт.

**Осознанное упрощение.** Запоминание мастер-пароля («помнить сутки/неделю»)
реализовано только на Windows — через DPAPI, шифрование средствами системы под
текущую учётную запись. На Linux и macOS запоминания нет: класть пароль
открытым текстом нельзя, а тащить ради этого лишнюю зависимость незачем —
рабочая платформа у приложения одна, Windows.

## 2026-09-15 — Таймер считает от запрошенного окна, а не от фактического

**Решение.** Обратный отсчёт ведётся от `FW_TIMEOUT` стойки, а если он не задан —
от умолчания демона (`FW_ACCESS_TIMEOUT`, 30 с). Таймер показывается всегда.

**Почему.** Клиент SPA «стреляет и забывает»: ответа от сервера нет, узнать
фактическую длительность окна неоткуда. Демон применяет запрошенное значение,
но не выше своего потолка `MAX_FW_TIMEOUT` (по умолчанию 300 с).

**Осознанное упрощение.** Таймер в обоих случаях показывает ожидаемое, а не
фактическое: если сервер срезал окно по потолку или у него другое значение
`FW_ACCESS_TIMEOUT`, отсчёт разойдётся с действительностью. Показать ожидаемое
полезнее, чем не показать ничего; сказано в README и в подсказке у поля.

## 2026-09-15 — Интерфейс собирается в один самодостаточный index.html

**Решение.** Vite собирает стили и скрипт внутрь единственного HTML-файла
(`vite-plugin-singlefile`).

**Почему.** Модульные скрипты, загружаемые по `file://`, браузерные движки
блокируют — окно вебвью в собранном приложении осталось бы пустым. Встроенный
код работает везде, и упаковка упрощается до одного файла.

## 2026-09-15 — fwknop.exe собирает CI, клиент кладётся в архив рядом

**Решение.** Готовых сборок под Windows проект fwknop не публикует — в релизах
только исходники. Поэтому `fwknop.exe` собирается из официального архива
кросс-компилятором mingw-w64 на стороне GitHub Actions
(`build/fwknop-windows.sh`) и кладётся в портативный архив рядом с `FWKOG.exe`.
В репозитории чужих бинарников не лежит.

**Почему не скачивать при запуске.** Качать пришлось бы из нашего же релиза
(других доверенных источников нет), то есть собрать всё равно нужно, но плюсом
появились бы зависимость от интернета при первом запуске и проверка подписи.

**Что пришлось указать сборщику** (сам код fwknop не меняется):

| Ключ | Зачем |
|---|---|
| `--disable-execvp` | В Windows нет `fork`/`pipe`/`waitpid`. Клиент умеет запасной путь через `popen()`, этот ключ его и выбирает. |
| `ac_cv_func_fstat=no` | Отключает проверку прав rc-файла: она про права Unix (`getuid`, `S_ISLNK`), в Windows смысла не имеет — в сборке автора под Visual Studio её тоже нет. |
| правка `common/Makefile.in` | В исходниках статической библиотеке ошибочно передаются ключи `-lwsock32 -lws2_32`; современный `ar` такое отвергает. Правка снимает их — на итоговую программу это не влияет, библиотеки подключаются при сборке exe. |
| `-Wl,-Bstatic -lssp` | Защита стека прилинковывается статически, иначе рядом с exe потребовалась бы `libssp-0.dll`. |

Скрипт проверяет контрольную сумму архива с исходниками и то, что собранный
exe не тянет посторонних библиотек.

## 2026-09-15 — Приложение портативное, данные — нет

**Решение.** `FWKOG.exe` носится с собой, а стойки остаются на машине в
`%LOCALAPPDATA%\FWKOG\`. Перенос — отдельным зашифрованным файлом экспорта.

**Почему.** Секреты, которые ездят на флешке вместе с программой, теряются
вместе с ней. Осознанный экспорт — это явное действие человека, а не побочный
эффект копирования папки.
